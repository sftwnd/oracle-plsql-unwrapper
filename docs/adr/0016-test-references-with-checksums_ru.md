# 0016. Тестовые эталоны байт в байт и манифест контрольных сумм

[English version](0016-test-references-with-checksums.md)

## Контекст

Тесты побайтово сравнивают результат unwrapper с эталонами: единицами, завёрнутыми WRAP (`<образец>.wrapped`), и
текстами, в которые они восстанавливаются (`<образец>.unwrapped`), в каталоге `samples` формата. В эталоне важны именно
байты. WRAP для Windows пишет CRLF, а WRAP для Linux — LF, образец с возвратами каретки смешивает их с одиночными CR,
строки завёрнутой единицы кончаются пробелами, скрипт может кончаться без перевода строки, а единица V2 — содержать NUL
или текст в UTF-8. Все эталоны синтетические: их текст принадлежит проекту, и WRAP того же выпуска снова строит из него
хранимую единицу.

Git и редакторы меняют как раз эти байты. При `core.autocrlf=input` git заменяет CRLF на LF, когда файл добавляется;
при `core.autocrlf=true` — умолчании Git for Windows и Windows-раннеров GitHub, на которых `native.yml` запускает
`verify`, — заменяет LF на CRLF при checkout. Такое изменение не видно в `git status` и одинаково меняет завёрнутую
единицу и её эталон: тесты проходят, но уже не проверяют перевод строки, с которым единица записана. Редакторы удаляют
пробелы в конце строк и добавляют перевод строки в конец файла.

Эталон — это ещё и то, что читает ревью исправления: изменение unwrapper видно как строки эталонов, которые оно меняет.

## Решение

- Эталон хранится как есть, байт в байт, так, как его записал WRAP или восстановил unwrapper; `Samples.read` читает
  байты.
- `.gitattributes` задаёт `-text` для `*.wrapped`, `*.unwrapped` и `SHA256SUMS`: git не преобразует их переводы строк
  при любом `core.autocrlf`. Для эталонов он задаёт `-whitespace`: `git diff` и `git apply` не считают их пробелы и CR
  ошибками, а `git apply --whitespace=fix` их не трогает. `*.wrapped` помечен `linguist-generated`: GitHub сворачивает
  вывод WRAP в pull request.
- `.editorconfig` не даёт редакторам удалять пробелы в конце строк эталонов и добавлять перевод строки в их конец.
- В каталоге эталонов лежит манифест `SHA256SUMS` в формате `sha256sum`: строка `<hash>  <путь>` для каждого эталона
  ниже него, по возрастанию пути. `ReferenceChecksums.mismatches` из тестового jar SPI сверяет каталог с манифестом в
  обе стороны и перечисляет все расхождения: файл из списка, которого нет или у которого другая сумма (с его нынешними
  переводами строк), и эталон, которого нет в списке. `SampleChecksumsTest` в V2 проверяет `samples`.
- Проверка выполняется в модуле — хозяине эталонов. У проекта, который берёт тестовые jar нескольких форматов,
  каталоги `samples` их всех лежат под одним путём classpath.
- Эталон меняется вместе со своей строкой манифеста. Манифест пересобирается в своём каталоге командой
  ```
  find . -type f \( -name '*.wrapped' -o -name '*.unwrapped' \) | sed 's|^\./||' | LC_ALL=C sort \
      | xargs shasum -a 256 > SHA256SUMS
  ```
  и проверяется без Java командой `shasum -a 256 -c SHA256SUMS`.

## Обоснование

- Байты как есть дают ревью строки, которые меняет исправление, позволяют git хранить единицы одного исходника,
  завёрнутые несколькими выпусками, как дельты друг друга, и делают новым образцом сам файл WRAP, без инструмента
  кодирования.
- Атрибуты сохраняют байты там, где их изменил бы git; манифест показывает изменение, откуда бы оно ни пришло: git без
  атрибутов, редактор, копирование, фильтрация ресурсов Maven. Проверка читает эталоны из `target/test-classes` — ту
  копию, которую читают тесты.
- Манифест сверяется в обе стороны, поэтому сборку валит и эталон, добавленный без суммы, и файл другого происхождения,
  попавший к эталонам.
- SHA-256 в формате `sha256sum` не требует инструмента проекта: манифест строит и проверяет стандартная команда.
- Один манифест на каталог эталонов, а не на каждый подкаталог: эталон, переехавший в другой подкаталог, меняет одну
  строку.

## Альтернативы

- **Zip-архив в Base64 для каждого эталона.** Сохраняет байты при любом checkout, потому что декодер пропускает переводы
  строк, и скрывает текст от прямого чтения, что важно лишь для кода, который нельзя публиковать. Правка одной строки
  переписывает в диффе весь файл, git не может хранить такие файлы дельтами, а новому эталону нужен инструмент
  кодирования. Эталоны синтетические, скрывать нечего.
- **Перевод строки в имени эталона (`_lf`, `_crlf`).** Повторяет то, что определяет сборка WRAP, и не имеет имени для
  образцов со смешанными переводами строк — тех, для которых переводы строк важнее всего. Имя утверждает байты, но не
  сохраняет их.
- **Расширения `.sql` и `.plb`.** IDE считает такой файл SQL: проверяет его инспекциями, а переформатирование каталога
  переписывает его байты. Собственные расширения эталонов к тому же отделяют их от завёрнутых и восстановленных файлов
  любого другого происхождения.
- **Только `.gitattributes`.** Предотвращает преобразования git, но не изменения редактора или инструмента, и не
  оставляет ничего, что показало бы изменение.

## Последствия

- Исправление, которое меняет эталон, меняет его строку в `SHA256SUMS`, и дифф манифеста перечисляет эталоны,
  изменённые исправлением.
- Сборка падает, если эталон расходится с манифестом, и называет файл и его переводы строк.
- Дифф показывает CRLF как `^M`, а единицу с NUL — как двоичный файл.
- Новому виду эталона, с другим расширением, нужна строка в `.gitattributes`, в `.editorconfig` и в
  `ReferenceChecksums`.
