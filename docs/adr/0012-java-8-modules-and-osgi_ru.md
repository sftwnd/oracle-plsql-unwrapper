# 0012. Уровень Java 8, модули JPMS и бандлы OSGi

[English version](0012-java-8-modules-and-osgi.md)

## Контекст

Библиотеку запускают там, где живут старые установки Oracle, поэтому она должна работать на Java 8. При этом приложение
на JDK 9 и новее должно получать настоящие модули с закрытым внутренним устройством, а контейнер OSGi — настоящие бандлы.
Форматы — это сервисы (ADR 0011), поэтому каждый из трёх способов запуска должен их находить.

## Решение

- Весь код и тесты — на уровне Java 8, и по языку, и по API: JDK 9 и новее компилируют с `release 8`, который проверяет и
  API. JDK 8 компилирует с `source` и `target`.
- `src/main/java9/module-info.java` модуля компилирует профиль `java9-modules`, активный на JDK 9 и новее, в
  `META-INF/versions/9`, с `release 9`, а манифест содержит `Multi-Release: true`. Компиляция идёт в фазе
  `prepare-package`: дескриптор в `META-INF/versions/9` в `target/classes` не находится, а в этой фазе реактор отдаёт jar
  нужных модулей. Классы модуля попадают в javac через `--patch-module`.
- На JDK 8 та же сборка делает jar без дескриптора. В их манифесте есть `Automatic-Module-Name`, поэтому они работают как
  автоматические модули с теми же именами.
- `maven-bundle-plugin` строит заголовки OSGi каждого модуля в фазе `process-classes`. Экспортируются только пакеты SPI и
  API. Форматы связываются через OSGi ServiceLoader Mediator: формат имеет `Provide-Capability: osgi.serviceloader` и
  требует расширение `osgi.serviceloader.registrar`, unwrapper требует `osgi.serviceloader.processor` и сервис. Такой
  посредник — Apache Aries SPI Fly.
- Дистрибутив unwrapper — `target/<artifact>-<version>-dist.zip`, с тем же содержимым в каталоге
  `target/<artifact>-<version>-dist`: `LICENSE`, исполняемый jar и запускающие его `bin/unwrapper`, `bin/unwrapper.cmd`.
- Jar модулей остаются в `target/<artifact>-<version>-modules`, для запуска на module path и для `jlink`.
- Рядом с обычным jar у unwrapper есть исполняемый jar со всеми классами, `target/<artifact>-<version>-all.jar`, для
  `java -jar` на любом JDK. Его собирает `maven-assembly-plugin` по `src/assembly/executable-jar.xml` модуля
  `oracle-plsql-unwrapper`: манифест новый, поставщики в `META-INF/services` слиты, а `META-INF/LICENSE` — тот, что в
  jar unwrapper, как есть. SPI и форматы под той же лицензией свой текст не кладут. Обработчик `file-aggregator`
  плагина `maven-assembly-plugin` для лицензии не используется: он пишет в файл время сборки, и исполняемый jar и
  дистрибутив отличались бы от сборки к сборке. `UnwrapperLaunchIT` проверяет, что текст лицензии у обоих — файл
  `LICENSE`.
- `UnwrapperLaunchIT` запускает собранный дистрибутив и исполняемый jar в отдельной JVM каждым из этих способов.

## Обоснование

- Дескриптор multi-release не виден Java 8 и старым инструментам, читающим все классы jar, в отличие от
  `module-info.class` в корне jar.
- `release` ловит вызов более позднего API при компиляции. С одними `source` и `target` сборка на новом JDK прошла бы, а
  на Java 8 всё упало бы во время выполнения.
- Профиль по JDK оставляет сборку рабочей на JDK 8, где `module-info.java` не компилируется.
- Манифест строится до появления дескриптора, поэтому bnd берёт `osgi.ee` из классов Java 8.
- ServiceLoader Mediator позволяет одному поставщику обслуживать все три способа: в коде нет типов OSGi и зависимости от
  них, а `META-INF/services` остаётся единственным списком поставщиков.
- Дистрибутив из одного jar проще всего передать, а запуску из консоли модули ничего не дают: результат тот же. Модули
  важны приложению, встраивающему библиотеку.
- Один файл — самый простой способ запустить инструмент, а обычные jar остаются модулями и бандлами, и от них зависит
  модуль `oracle-plsql-unwrapper-pro`.
- Манифест части называет её бандл, её модуль и jar рядом с ней. Для исполняемого jar всё это неверно.

## Альтернативы

- **Более высокий уровень Java и отдельная сборка для Java 8.** Две версии кода, которые надо согласовывать.
- **`module-info.class` в корне jar.** Старые сканеры классов на Java 8 падают на классе версии 53.
- **`moditect-maven-plugin`.** Он добавляет дескриптор в готовый jar, но javac его не проверяет, и в сборке на один плагин
  больше.
- **Генерация дескриптора через `-jpms-module-info` в `bnd`.** Дескриптор был бы выведенным, а не написанным, а `provides`
  — именно то, что должно быть на виду.
- **Declarative Services или `BundleActivator`.** Код формата зависел бы от OSGi.
- **Только исполняемый jar со всеми классами.** Он не может быть несколькими модулями и бандлами, а
  `oracle-plsql-unwrapper-pro` нужен обычный jar.
- **Jar модулей в дистрибутиве и скрипт, выбирающий module path.** Больше файлов при том же результате.
- **`maven-shade-plugin`.** Он сохраняет манифест основного jar, и результат выдаёт себя за бандл и модуль.

## Последствия

- Нет record, выражений `switch`, `var`, `List.of` и API новее Java 8. Классы значений пишутся вручную.
- `./mvnw compile` дескрипторы не компилирует, это делают `package` и `verify`.
- Ошибка в дескрипторе обнаруживается только сборкой на JDK 9 и новее; её покрывают тесты на module path.
- Jar, собранный на JDK 8, не имеет дескриптора: для закрытого внутреннего устройства собирайте на JDK 9 или новее.
- Исполняемый jar работает только на classpath: у него нет дескриптора и заголовков OSGi.
- `jlink` собирает образ unwrapper из `target/<artifact>-<version>-modules`. Ему нужно добавить `jdk.charsets`: эти
  кодировки использует V2. Сборка этого не делает: образ создаётся под одну платформу.
- Профили `native` и `native-linux` родителя собирают исполняемый файл unwrapper из его исполняемого jar через
  `native-image` в каждом модуле с `native.skip=false`: здесь в `oracle-plsql-unwrapper`, а в одноимённом проекте — в
  `oracle-plsql-unwrapper-pro`. Они собирают для системы сборки и для Linux x86_64 в контейнере GraalVM на Oracle Linux 10, чей файл требует
  glibc 2.34. `native-image` собирает только под ту систему, где запущен.
- Формат приносит опции образа в `META-INF/native-image` своего jar: V2 просит `-H:+AddAllCharsets`, кодировки своих
  текстов. `native-image` читает их из каждого jar, поэтому их получает любая сборка образа, а поставщиков он сам находит
  в `META-INF/services`.
- В OSGi приложению нужен посредник в контейнере, иначе бандл unwrapper не разрешится.
- JDK 25 ещё компилирует `release 8`, с предупреждением; для более позднего JDK, который это уберёт, понадобится toolchain.
